## 16. Troubleshooting

| Symptom | Fix |
|---|---|
| `Login failed` / `No password configured` | Examine the value of `AS_KEYSTONE_PASSWORD` in `.env`. |
| `ANTHROPIC_API_KEY is not set` | Add the key to `.env`. As an alternative, use `--model scripted`. |
| `No fixture for keystone` | Run `python -m harness capture keystone`. |
| `SKIPPED - Live writes need AS_ALLOW_WRITES=1` (from `harness run`) or `refused: Live writes need AS_ALLOW_WRITES=1` (from `harness restore`) | This is the intended behaviour. Set `AS_ALLOW_WRITES=1` in the shell, for that one command only. The code does not read this variable from `.env`. See [The live write run](live-run.md#11-the-live-write-run). |
| ``refused: `ask --apply` writes only on the fake server`` | This is the intended behaviour. For live writes, use `harness run ... --live-apply`. |
| `SKIPPED - ... runs offline only` | The task uses fake-server faults or extra files. Run the task with `--target fake`. |
| `restore incomplete for [...]` | WARNING: Do this step only to complete an incomplete live restore. The command writes to the live platform. Run `AS_ALLOW_WRITES=1 python -m harness restore runs/<set>/<task>/snapshot-1.json --target live --live-apply`. |
| `conflicts_left_alone` in a restore report | Another team changed those fields during the run. The restore did not change them. Examine these fields by hand. |
| `pre-flight FAILED` (from `harness preflight`) or `Pre-flight failed; nothing was written` (in a `harness run` report) | The platform changed. Read the problems in the list. If you expected the change, capture the fixture again.<br>The problem `… is not in the fixture (outside the allow-list, …)` or `… changed since the fixture … (outside the allow-list, …)` is about a row in Incoming. The fixture does not contain this row, or the row changed. Before any live write, capture the fixture again. Then run TI2L offline again. |
| `warnings (not blocking):` after `pre-flight OK` (from `harness preflight`), or `pre-flight warnings (not blocking):` during a live write run | This is the intended behaviour. Each warning is about a row in Incoming that is outside the write allow-list. The fixture contains the row, and the row did not change: `… will not be written or escalated`. Since 23 Sept, the expected number of warnings is **exactly 9**, 1 for each copy (O5). If the number is different, Incoming changed. Stop and capture the fixture again. |
| `… is new or changed since the fixture and is related to an allow-listed file (name, hash or document kind)`, `… is gone since the fixture and is related …`, or `… has left Incoming since the fixture` (pre-flight problem) | Something on the platform changed. This change can affect the decisions about the 9 files. Stop.<br>Find what changed and who changed it. Capture the fixture again (`python -m harness capture keystone`). Derive the expectations of TI2L again. Run TI2L offline before you try again. |
| `folder '…' (…) was renamed, moved or archived since the fixture`, `… is not in the fixture`, `… is gone since the fixture`, `… changed since the fixture (updated_at …)` or `N folders are named '…'` (pre-flight problem) | A folder changed. Triage uses folder names to select the destination of each file, so the plan can change. Find who changed the folder. If the platform records this person, the problem gives the name.<br>Before any live write, capture the fixture again. Then run TI2L offline again. A folder that another team made for its own work also blocks the run. |
| `SKIPPED - TI2 is not marked live_write = true …` | This is the intended behaviour. Since 27 Sept, TI2 is an offline-only task. The live write task is TI2L. |
| `left for a person: not in this run's scope` in a tidy answer | This is the intended behaviour. The file is outside the write allow-list of the run. For the live write run, these files are the 9 copies of 23 Sept. Thus, the agent did not write to the file and did not escalate it. |
| `aborted: budget` / `aborted: max_turns` (from `harness run`), or `ABORTED budget` / `ABORTED max_turns` at the end of the `ask` status line | Increase the related limit in `.env`: `AS_MAX_MCP_CALLS`, `AS_MAX_USD` or `AS_MAX_TURNS`. |
| `SKIPPED - TI2L already ran live and may have sent writes (...)` | This is the intended behaviour. A live write task runs only 1 time. To undo that run, use `python -m harness restore`. Move the folder of that run out of `runs/` only if a second live run has approval. |
| `TI2L: an earlier attempt here sent no write; moved ... to .../attempt-<time>` | This is the intended behaviour. That attempt stopped before it sent anything. It stopped at set-up, login or pre-flight, or because of a model error before the first write. The harness moved the files of that attempt to a different folder. Then the new run continued. |
| `the fixture was captured at ..., not within the last 24 hours` (pre-flight problem) | Immediately before the live write run, capture the fixture again (`python -m harness capture keystone`). Then run TI2L offline as a rehearsal. Then run `python -m harness preflight`. |
| `the description or read-only mark of a tool the agent uses changed since the fixture` (pre-flight problem) | The platform changed a tool that the agent uses. Before any live write, capture the fixture again. Then run TI2L offline again. |
| `refused: no write journal at ...` (from `harness restore`) | The restore needs the `writes-N.json` file next to the snapshot. Add `--no-journal` only if this file does not exist any more. With `--no-journal`, the restore restores the snapshot values only on the rows that this seat changed last. |
| `warning: stale definition: ...` (from `harness rescore`) | A file in `harness/tasks` changed after the harness scored this set. The rescore still uses only the data in the run files. To score the set against the current task file, run the set again. |
| `Another seat changed its <fields> at the same moment; check the file by hand.` in a tidy answer | Another team changed fields that the agent did not write. This change occurred while the write of the agent was in progress. The platform has no compare-and-set (see [14](known-limits.md#14-known-limits-and-open-questions)). The move of the agent was successful, so examine the file. |
| `N possible secret(s) found` (from `scripts/secret_scan.py`) | Open the file that the output names, at the line that it gives. If the value is a real secret, remove it from the file. Then rotate the secret (replace it with a new secret). Tell the team. If the value is a harmless example, add it to `ALLOWED` in the script. |
