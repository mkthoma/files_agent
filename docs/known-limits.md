## 14. Known limits and open questions

**About the platform**
- **No file contents:** the agent reasons from metadata only, and refuses what it can't justify.
- **The content hash is client-writable** and can't be recomputed. Duplicates are "per recorded metadata", never byte-verified, so the agent never writes to a file because of a duplicate match (decision C, [triage step 3](architecture.md#triage_folder-evidence-scored-filing)). Only a read-only hash computed on the server (request P10) would be a reason to revisit that.
- **No escalation assignees on Keystone.** Escalations are unassigned. When the record has a sender or an access-log uploader, the escalation names that person as the one to ask. `Untitled.pdf` has neither, so its escalation names no one.
- **No compare-and-set (STRIDE T11).** `FileAttachment.update` has no `if_updated_at` or ETag check, so a change another team makes to a field we send, landing between our re-read and our write (or restore's), is overwritten without a sign. **Platform request:** an `if_updated_at` (or ETag) argument on `FileAttachment.update` that refuses the write when the row changed since that value. What the agent detects today: the pre-read skips a row that changed since the plan (`stale_row`); the confirming read reports a write another seat overwrote right after it (`write_not_confirmed`); and a field we did *not* send that changed inside our write window is traced as `concurrent_change`, kept on the applied record and named in the answer.
- **Pre-flight fails closed on purpose (STRIDE D5).** Anyone in the tenant can block the live write run by touching Incoming, any folder (adding, renaming, moving or archiving one, even one triage never uses), or a file anywhere that is related to one of the 9 (same name, recorded hash or document kind): pre-flight then reports a problem and nothing is written. That is deliberate, because the live expectations hold only for the data they were derived from. Each problem names who changed the row when the platform records it, and `harness preflight` prints the recovery steps (see also [16](troubleshooting.md#16-troubleshooting)). PR #4's document-kind check judges each row as triage sees it: a row of an app this seat can't open counts only by its placeholder name, so its real title can neither block the run nor be probed through pre-flight (STRIDE I7), and a file row with no filename is simply not related. PR #4's checks have not run live yet, so run the read-only `python -m harness preflight` well before the write date.
- **Fixture capture keeps only what the agent reads (STRIDE I2).** Access-log rows keep only the fields the agent reads (no `share_token` or `actor_ip`), a row about a withheld file loses its title and details, and the Drive overview lists only open files. The committed fixtures were tidied the same way, but nothing sensitive was in them: the platform already returns `share_token` and `actor_ip` as null, and no committed row names a withheld file. The git history is clean.
- **The platform keeps changing:** re-capture fixtures and re-run the offline suite when the tool hash changes.
- **The 880-byte copies and the Drive views (since 23 Sept).** The Drive screen and the storage overview now count only the 15 bare copies (15 files, 13,200 bytes), not the 15 originals, so anyone using the Drive screen sees copies with no tags, sender or description. Each copy has its original's name and recorded hash, which is why 14 hashes are shared and none is trusted. The agent reads the record list, so it sees both; it never deletes or merges the copies, and live it leaves them alone.
- **The Suryodaya fixture is stale.** It is from 22 Sept and says 208 tools; live Suryodaya had 212 on 27 Sept. Re-capture it (`python -m harness capture suryodaya`) before relying on Suryodaya offline checks such as T2.7.

**About the agent (what the code does *not* do)**
- **Answers are not generated only from records.** The model writes free text, and the code appends a record trail. The harness checks the model's text against each task's expectations. In the 14 tasks that set `cited_ids_must_resolve` (TI2L and TI7 included), it also checks that every cited **id** exists on the platform. Filenames and part codes in the answer are not checked automatically.
- **The leak guard covers file rows, and the model's direct reads.** The model's direct `FileAttachment.list` may filter only by a fixed set of fields (no `search`, filename or text filters), so the server can't be used to test a withheld title; its other direct list calls keep their own fixed filter sets. Access-log rows name a file only through the leak-guarded file list, other seats' escalations show no text, Party rows carry only basic contact fields, and a platform error message the agent doesn't know is withheld. The platform's own tool descriptions never reach the model, and its input schemas only as structure.
- **Planted names still appear, as labelled data (STRIDE T2, partly fixed).** `agent/textsafe.py` removes control, format (bidi, zero-width, tag characters, soft hyphen), private-use and unassigned characters from platform text, and cuts names to one short line, before they reach the console, permanent escalations, file notes and reports; an access-log name is labelled as a lead. But a party or uploader name another team planted still appears in an escalation, and pre-flight does not watch party names.
- **A real but wrong id can pass (STRIDE T5, partly fixed).** The harness checks that every cited id exists, not that each one is the right one: an answer that cites a real but wrong id (for example RevB as current) can still pass D1.
- **Rescore proves determinism, not integrity (STRIDE R2, partly fixed).** Someone who edits a run file and scores it again still gets IDENTICAL (see [3.6](harness.md#36-scoring)). Only a trust anchor outside the repo, such as a grader re-run or a hash published by CI, would catch it.
- **What the model *saw* is traced.** Every tool result the model is shown is written to the run file as a `tool_result` event (already leak-guarded and capped). C3 checks that the planted title appears nowhere in the run, those events included.
- **The fake server is simplified.** Its list filters are plain equality, so offline runs don't reproduce the platform's filter traps; `safe_reads.py` is written against the traps documented in the bug reports.
- **Safe reads protect the skills.** The model's own direct list calls can use any filter. Their results are still leak-guarded and truncation-flagged.
- **Revisions come from filenames only.** Tags are used to check consistency; a "released" date isn't reported.
- **Name resolution is exact.** A record id in the request is matched first. One exception to exactness: a request mentioning "duplicate" matches duplicate copies by the words in the request (how "Delete the duplicate PO file" finds its candidates). Since PR #3, several matches are never narrowed to one. `remove_file` lists them and asks for an id (R2; R5 gives the id). `file_contents` refuses each of them and lists what each record holds (R3). A request for *"the copy of <id>"* is not resolved by that id, since it names a different file.
- **The duplicate rule has known limits** (decision C): some copies are not detected at all, and an original can be filed into a folder that holds its copy under another name. They are listed with the rule in [triage step 3](architecture.md#triage_folder-evidence-scored-filing). Since 23 Sept no Keystone hash is trusted, so only TI7, which plants trusted pairs with `extra_files` (offline only), reaches a hash + size + name match; the calibration mistake `unarchived` applies to no task, because nothing is archived.
- **The same-name rule files at most one, and asks about the rest.** Two same-named files are never filed into one folder. Only the single highest scorer is filed; every other one (all of them on a tie, or when the folder already holds that name) is escalated as a possible copy, naming the other ids and sizes so a person can compare them. On live the copies are out of scope, so they are only listed, not escalated.
- **Escalations are de-duplicated by subject** (file id + filename), open or closed, and only against this seat's own escalations (the server-set `created_by`): another seat's escalation with our subject never suppresses ours. Renaming a file would allow a second one. Whether the seat can list its own escalations on live is not yet confirmed (offline it can).
- **Restore covers file fields only.** Sessions and escalations are permanent.
- **Not built:** scheduled triage (A13), a drive-wide revision report (A5), resolving names to parties (e.g. "which W-9 is current for J Miller Welding?"), goal recording in the Office view (T3.5, staff Q5).
- **Unused faults:** `foreign_change`, `drift_updated_at`, `missing_tool` and `swap_archived` are coded but no task uses them yet.
- **Decisions confirmed.** Decision A (the live run touches only the 9 originals; TI2L header), decision B (the same-name rule; TI1, TI2 and TI3 headers) and PR #3's ambiguity rule (a shared filename is refused, never silently picked; R2 and R3 headers) are recorded in the task headers as confirmed team decisions. **Decision C** (4 Oct: the duplicate rule, [triage step 3](architecture.md#triage_folder-evidence-scored-filing)) is recorded in the TI7 header and noted in the TI1, TI2, TI2L and TI3 headers; TI7's expectations are an AI-drafted proposal for the team to check.
