## Security review (STRIDE)

> **The team must review this** before relying on it. The full report is [`docs/security/stride-review.md`](security/stride-review.md).

On 2–3 Oct 2026 the agent and the harness were reviewed with **STRIDE** (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Each threat was reproduced offline with a proof-of-concept script against the real code, challenged by a skeptical reviewer, fixed where that was safe, and checked again with the same script. The live platform was never touched.

- **54 threats:** 5 S, 14 T, 10 R, 12 I, 10 D and 3 E. **None is critical.** The highest verified risk is 4 out of 16 (Medium), mostly because plan-only mode, the 9-file allow-list, the two live-write switches and the leak guard already made attacks hard to reach.
- **49 fixed, 4 partly fixed, 1 accepted by design.**
  - Partly fixed: **T2** (a name another team planted still appears in an escalation, cleaned to one labelled line), **T5** (a model that cites a real but wrong id still passes), **T11** (the platform has no compare-and-set; a platform request) and **R2** (someone who edits a run file and scores it again still gets IDENTICAL; that needs a trust anchor outside the repo).
  - By design: **D5**. Pre-flight fails closed, so any tenant user can block the live write run.
- Every guard in the code carries a `# STRIDE <id>` comment. [Round 6](history.md#15-changes-after-review) lists the changes by area.
- **The graded behaviour is unchanged.** On the tree merged with PR #4, offline: 21 of 21 tasks pass ×5, rescore IDENTICAL, routes 10 / 10, calibration 355 of 355 (it grew from 295 with the new checks), and the 78 hand-written tests pass. On the tree that added PR #5's tests (3 Oct), all 157 passed. (Decision C, 4 Oct, then added TI7: 22 of 22 and 377 of 377; see [Round 7](history.md#15-changes-after-review).)

**Behaviour changes operators must know:**

| Area | What changed |
|---|---|
| Live write gate | `--live-apply` without `--target live` is refused (exit 3), for `run` and `restore`. A live write task is refused if an earlier live attempt may have sent a write; an attempt that provably sent nothing is moved to `attempt-<time>/`. `--set` must be a plain folder name under `runs/`. A live write needs the write journal. |

Only escalations this seat created (the server-set `created_by`) suppress a new one. |

## Ground rules (old section 6.1)

These rules were part of section 6.1 of the old README. The rest of 6.1 is in [plan-and-status.md](plan-and-status.md#61-whats-graded-and-the-ground-rules).

**Ground rules**

1. **Build your own loop.** The model is called through the plain Messages API over HTTPS, using only Python's standard library (`urllib`). There is no SDK and no agent framework, so there is nothing to install. The MCP client is hand-written. ✅ `agent/model.py`, `agent/mcp_client.py`
2. **Only skills write.** The model plans and explains. Code in the 8 skills (run by the harness tasks and by your hand-written tests in `tests/`) does every agent write, through the write guard (`agent/guards.py`). The only other writes are the restore after a live write run (`agent/snapshot.py`), which puts back only fields this seat wrote. The agent has only 3 write tools: `FileAttachment.update`, `AgentSession.create` and `AgentEscalation.create`. **Plan-only is the default.** ✅
3. **Keystone is shared.** Live writes can touch only the 9 allow-listed Incoming files, and only while they are still in Incoming when the run starts. The agent neither writes nor escalates any other file (since 27 Sept that includes the 9 copies of 23 Sept). Live writes go through the harness only, as the single run of TI2L:
   `AS_ALLOW_WRITES=1 python -m harness run TI2L --target live --model anthropic --live-apply --set live-write` (the full steps are in [7.6](live-run.md#76-before-during-and-after-the-live-write-run) and [11](live-run.md#11-the-live-write-run)).
   Set `AS_ALLOW_WRITES` in the shell for that one command; `.env` is ignored for it. `python -m agent ask --apply` works only with `--target fake`. The harness runs pre-flight, saves `snapshot-N.json` and a write journal `writes-N.json`, and restores in a `finally` block. ✅
4. **Tests and the definition of "correct" are yours.** You write `tests/` by hand. The task expectations (`harness/tasks/*.toml`, `harness/tasks/routes.toml`), the scoring rules (`agent/filing_rules.toml`) and the checks (`harness/verifiers.py`) exist today as **AI-written drafts**. Review them, change them and commit them yourselves. AI help is for plumbing only, and only if staff say yes to Q3 (the code assumes yes). Optionally, block AI edits to your paths (T0.5, not set up yet). 👤

## 8. Safety on the shared platform

Keystone is shared with other teams. These rules are enforced in code (the STRIDE review of 2–3 Oct checked each one against the code; see [Security review (STRIDE)](#security-review-stride)):

1. **Plan-only by default.** Nothing is written unless you ask for it. `python -m agent ask --apply` writes **only on the fake server**; on live it is refused.
2. **Live writes go through the harness only**, and need `--target live`, `--live-apply` **and** `AS_ALLOW_WRITES=1`, set in the shell for that one command (the same for `harness restore`). `--live-apply` without `--target live` is refused, never run quietly on the fake server. The `.env` file is ignored for the switch, so it can't stay on by accident. Live writes are only ever allowed on Keystone. In code, the write guard refuses any live write while no write journal is attached, the runtime accepts only the targets `live` and `fake`, and any transport that is not the fake server gets the 9-id cap, whatever it is called.
3. **Row-id allow-list.** Only the 9 verified Incoming files (`agent/config.py`) can be written, and only while they are still in Incoming when the run starts. A new file that appears in Incoming is not writable.
4. **Nothing outside the allow-list is written or escalated** (since 27 Sept). Triage records such a file as `out_of_scope` and lists it for a person; the Escalator refuses to escalate it, because escalations are permanent. On live Keystone this keeps the 9 copies of 23 Sept untouched. TI2L rehearses this offline.
5. **Only 3 write tools exist for the agent:** `FileAttachment.update`, `AgentSession.create` and `AgentEscalation.create`. There is no delete path. The MCP client refuses any other tool that the catalogue doesn't mark read-only, and the guard writes only `folder_id` and `description`. The agent never archives: a possible copy is escalated, never written (decision C, [triage step 3](architecture.md#triage_folder-evidence-scored-filing)).
6. **Pre-flight before live writes.** The harness aborts if the tool catalogue changed (including the description or read-only mark of a tool the agent uses), if the fixture was not captured within the last 24 hours, if any folder was added, removed, renamed, moved, archived or otherwise updated since the fixture (or two folders share a name), or if any of the 9 files is missing from Incoming, changed since the fixture or no longer tagged `untriaged`. Any other row in Incoming is judged too: one the fixture knows and that hasn't changed (today, the 9 copies) is only a **warning**, printed and traced; an unknown or changed one is a **problem** and aborts the run, because it could change how the 9 are judged. For the same reason, a row in any folder that is new, changed or gone since the fixture and is related to one of the 9 (same name, recorded hash or document kind: doc type, or drawing code prefix), or was related before it changed, is a problem, as is a fixture row that has left Incoming or a fixture without a tool hash or a folder table. Each problem names who changed the row when the platform records it, and names a row of an app this seat can't open only by its placeholder. Pre-flight fails closed on purpose (see [14](known-limits.md#14-known-limits-and-open-questions)).
7. **Snapshot, write journal and restore.** Live write runs snapshot the 9 rows, save an empty `writes-N.json` before the first write and every write as soon as its call ends (an errored one as `uncertain`), and restore in a `finally` block, even if collecting the after-state fails.
8. **Restore doesn't overwrite other teams' changes it can see.** Each row is re-read just before it is put back. Only the fields the agent writes (`folder_id`, `description`) can be restored, and only where they still hold the value we wrote; anything else is reported under `conflicts_left_alone` and left alone. A description goes back to the text our note was appended to, so an edit another team made between the snapshot and our write survives (reported under `kept_foreign_edits`); every other field goes back to its snapshot value. Restore refuses a snapshot or journal it could not have written (ids outside the allow-list, unknown fields, wrong types, a cut-off file, or a snapshot taken on the other target), and one failed row doesn't stop the others. A journal written before decision C holds `is_archived` and is refused on purpose, nothing restored, with a message to restore it with the commit that made the run (the run manifest's git commit, 8202cf8 or earlier). So merge decision C before the live write run, not between that run and a later standalone restore. If the write journal (`writes-N.json`) is missing, `harness restore` refuses; only with `--no-journal` does it put back the rows this seat changed last.
9. **Only TI2L may write live; fake-server-only tasks never run live.** A write task runs live only if its task file says `live_write = true` (only TI2L does; TI2 is offline-only since 27 Sept). Tasks with `faults` or `extra_files` are refused on `--target live`.
10. **Escalations and sessions are permanent.** This seat can't delete them, so live write tasks run **once**; repeated runs happen offline. The harness enforces it: a live write task is refused while any earlier live attempt (in any run set) may have sent a write. An earlier attempt that provably sent nothing (its set-up or pre-flight failed, or it stopped before its first write) is moved to `runs/<set>/<task>/attempt-<time>/`, and the run goes ahead.
11. **A write is never resent after an unclear failure.** After a 5xx or a timeout it may already have happened, so the transport retries writes only on `429`. A write whose call errored, or whose reply was malformed, is journaled as `uncertain` (it may have landed), not forgotten. An escalation or session create that failed is read back; if it can't be found, it is never sent again in the same run, and the next run's fresh listing settles it.
12. **Secrets never reach disk.** Passwords, tokens and keys are redacted from every trace, and their `repr` is masked, so a traceback printed with its locals can't show them either. Block D (7.2) and `.githooks/pre-commit` check for leaks.
13. **Other teams' text is cleaned before it is printed or stored.** File, folder, party and uploader names are cut to one printable line (`agent/textsafe.py`) before they reach the console, a permanent escalation, a file note or `report.md`, and an access-log name is labelled as a lead, not a fact.
